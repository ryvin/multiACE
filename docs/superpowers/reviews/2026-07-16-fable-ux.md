# multiACE — Critical Ease-of-Use Review

**Lens:** "best-of-class EASE OF USE, least amount of errors" for ACE Pro + Snapmaker U1.
**Verdict:** The engineering is defensible; the product is not. multiACE is an expert system wearing a consumer UI. It answers the single most important user question — *"what filament is where, and can I trust it?"* — differently in every tab, sometimes wrongly, and sometimes it silently deletes the answer. The Exhibit-A pull failure is not an edge case; it is the direct consequence of the product having **no model for desired-vs-actual filament state**.

---

## 1. The worst ease-of-use failures, ranked

### #1 — The filament-identity pipeline lies to the user (Exhibit A)

**What the user experienced:** Pull reported "applied 2, 0 errors." The grid then showed no Red on slot 2, no names on occupied slots 0/1. Conclusion a reasonable user draws: *"it isn't displaying the right filaments"* → "Pull is broken."

**Why it actually happens — three stacked defects:**

1. **The backend garbage-collects labels on empty slots — silently.** In the deployed decay71 state builder (`/mnt/e/Code/multiACE/.decay71-ref/multiace/web/backend/main.py` lines 299–307), a slot with `gate == 0` starts an eject-debounce timer; after `EJECT_DEBOUNCE_S = 0.5` seconds (line 1961) `_drop_override_if_present(i, s)` **deletes the override and persists the deletion** to `slot_overrides.json`. Slot 0/2 had been empty for ages, so its debounce timer was long-expired: the very first `/api/plugin-api/state` poll after Pull — which is the plugin's own `render()` call in `pull()` (`filamenthub/static/app.js` line 150, `await render()`) — destroyed the "Red" label Pull had just written. **The UI's own refresh deletes what its own button just applied**, then reports "Pull complete: applied 2." No error, no event, no trace. This eject-drop was designed for a physical spool being pulled out mid-session; applied to tracker labels it means *a label on an empty slot can never exist for more than one poll cycle*, making "label-only mirror of FilamentHub's desired state" structurally impossible for any slot that isn't already physically loaded.

2. **The tracker and the sensors disagree, and nobody arbitrates.** FilamentHub says slots 2,3 hold Red/Pearl White; the ACE says slots 0,1 are occupied and 2 is empty. Pull ran anyway, wrote both labels, reported success. `plan_reconcile()` (`filamenthub/src/filamenthub_plugin/reconcile.py`) plans purely from FilamentHub winners vs. current override keys — **physical occupancy is not an input to the plan at all.** The `aces_covered` field ([] in the live payload) is never read anywhere in the plugin (`grep aces_covered src/` → nothing); prune scope is re-derived from winners' ACE indices (`known_aces`, reconcile.py line 43). So a schema-2 seam field that exists to declare coverage is dead weight, and the vacated-ACE gap (`ryvin/FilamentHub#18`) stays open.

3. **Even when a label survives, the plugin grid can't show what matters.** The FilamentHub tab renders only `s.material` (`filamenthub/static/app.js` lines 56–59) — the spool *name* ("SnapSpeed Pearl White") is mapped into `subtype` (`mapping.py` line 45) which the plugin grid never displays. Occupied-but-unidentified slots render the word **"loaded"** — a label carrying zero information — with no call to action. So the two slots that physically hold filament say "loaded," and the two slots FilamentHub knows about say nothing. That grid is worse than blank: it actively teaches the user the product doesn't know what it's doing.

**What the user should have seen instead:** a grid that says, per slot: *"A0: filament present — unknown. Tap to identify."*, *"A1: filament present — unknown."*, *"A2: expected SnapSpeed Red (not loaded)"*, *"A3: SnapSpeed Pearl White ✓ (RFID + FilamentHub agree)"* — plus a Pull result that says *"FilamentHub's loadout doesn't match what the ACE senses: 2 expected spools not detected, 2 detected spools unidentified. Review."* Full spec in §2.

### #2 — Four sources of filament truth, and the answer changes per tab

Identity can come from: RFID (`rfid_data`), manual/pull override (`_override_for`), derivation from the loaded head's print-task config (`_ptc_at(loaded_t)`, main.py line 342), and the `spool_cache` "Bound" badge in the ryvin console (`multiace_web/static/app.js` lines 2360–2374). The priority chain (override > RFID > derived) lives only in backend code; the user sees a tiny `src-badge` at best. Meanwhile:

- **Indexing is inconsistent between tabs on the same screen.** The main console is 0-based everywhere — `slotName` returns `Slot ${+i}` (`multiace_web/static/app.js` line 1881) and a code comment (line 2064) documents the deliberate 0-based convention; the FilamentHub tab is **1-based**: `ACE ${ace + 1} · slot ${slot + 1}` (`filamenthub/static/app.js` line 37). The same physical gate is "ACE A / Slot 2" in one tab and "ACE 1 · slot 3" in the next. During Exhibit A, a user cross-checking "which slot got Red?" between tabs is off by one *by design*. This alone can generate "it's showing the wrong filaments" reports with zero code defects.
- ACE naming also drifts: "ACE A (#0)" (dashboard), "ACE 1" (plugin, meaning ACE 0), `ACEA__Switch_0..3` (Fluidd macros where the letter is a *sort hack*, not the ACE letter — `ACEA__Switch_1` switches to ACE 1, not ACE A).

### #3 — Multi-ACE blindness: the flagship feature shows "?" most of the time

The product's whole point is multiple ACEs, yet the dashboard renders inactive ACEs as `is-stale` with a "stale" badge and every slot pill as `?` ("unknown gate_status (inactive ACE)", `multiace_web/static/app.js` lines 2320–2344). With the single-serial start-ACE constraint (CLAUDE.md instinct #1) this is honest — but the *presentation* is abandonment: no last-known snapshot, no "as of 14:02", no explanation in-place of what "stale" means or how to refresh it. A user with 3 ACEs sees 8 of 12 slots as question marks and concludes the product is broken. Honest uncertainty needs *timestamps and provenance*, not shrugs.

### #4 — Failure recovery is G-code incantations, not product

The known failure modes (CLAUDE.md instincts, project memory) all dump the user into a console:

- `head_source[N] == null` → head silently feeds the **wrong color mid-print** (memory: T3 printed purple instead of white). Recovery: know about and type `ACEC__Mark_Loaded_TN ACE=.. SLOT=..` — and re-run it after every Klipper restart because it's in-memory.
- `bookkeeping_empty` → the chevron item's *tooltip* says "recovery: ACE_CLEAR_HEADS HEAD=n from gcode console" (`multiace_web/static/app.js` line 2198). A tooltip. Pointing at a different application.
- Entangle-detect false trips every ~9mm on non-start-ACE heads (pre-0.82) → operator band-aid is `SET_PRINT_PREFERENCES FILAMENT_ENTANGLE_DETECT=0`, documented only in README/memory.
- README's own "Reset to clean state" is: unload via display → console command → **full power cycle**.

Credit where due: the load-feed-timeout banner (`renderStatusBanner`, lines 1512–1527) is genuinely excellent — it diagnoses past-grip drift and gives step-by-step physical recovery. That proves the team *can* do this. It's the exception, not the pattern.

### #5 — Drying has four competing UIs and auto-dry cannot work out of the box

To dry filament the user may encounter: (a) Fluidd `ACED__Dry_Start_0..3` macros, (b) the Dryer tab's profile cards, (c) the **legacy** single-FSM auto-dry panel still rendered at the top of the Dryer tab (`renderAutodryPanel`, `multiace_web/static/app.js` line 923 — Off/Log/Active modes, v1 state file that reads misleading "off" on v2 files per instinct #9), and (d) the Auto-Dry plugin tab (port 8090, per-ACE FSM). Two of these can disagree about whether auto-dry is even on. Then:

- Auto-trigger **requires a DIY Govee BLE→HTTP bridge** the user must build from `hardware-bluetooth.md` because the ACE's own humidity sensor returns `None` (autodry README lines 61–67). Without it, WATCHING never arms — and nothing in the UI says "auto-dry is inert because no humidity source is configured."
- Sensor→ACE mapping is **positional dict order** on a different machine's config (`GOVEE_BRIDGE_MACS`, README lines 83–90): get the order wrong and ACE 0's humidity silently drives ACE 1's dryer. No identity check, no UI to verify the mapping.
- The shipped default `target_pct=15` is below what the hardware achieves on the reference rig (memory: `FAILED_LIMIT` faults out of the box) — so the first unattended cycle ends in a sticky `FAULTED` state the user must discover and clear via `POST /reset-fault`.

### #6 — First-run landmines the installer knows about and doesn't defuse

README line 4: install without an ACE connected → printer unusable until you run `ACE_MODE_NORMAL`. Line 405: filament loaded before install "may cause unexpected behavior" — the user must know to `ACEC__Unload_All` first. `ace_device_count` ships commented-out, but multi-ACE without it risks locking the canonical map with a device missing (index drift → *commands go to the wrong ACE*). `default_park_retract_length_mm` defaults to Davinci-U1 geometry (700mm); wrong value physically jams the shared bowden or loses drive-wheel grip. Every one of these is a documented foot-gun the installer/UI could detect (no ACE at install; heads loaded at first boot; device count mismatch vs. enumerated USB) and instead delegates to README diligence.

### #7 — Cumulative drift is known physics handled reactively

Swap-park retracts drift neighboring slots until they lose grip (instinct #2). The product's answer is a per-slot "↺ Reseat" button that appears only *after* the ACE already reads the slot empty (`renderSlotCard` line 2423). Nothing counts swap-park cycles per slot, nothing warns "A1 has seen 14 retract couplings since last load — check seating before your next long print." Best-of-class means the machine tells you *before* the 3 AM mid-print failure, not offering a nudge button after.

### #8 — Developer vocabulary leaks into every user surface

"Pull complete: applied 2, 1 stale (not cleared)", "3 disputed slot(s) — resolve in FilamentHub: spool 31 also claims this (winner: 110)" (spool *IDs*, no names, no link), "bookkeeping_empty", "swap_in_progress", "SERIAL_WRITE_FAILED" in the Activity feed, badges "stale"/"Bound"/"Parked" with no legend, macro names `ACEC__Unload_T3` surfaced raw in confirms. Also a silent side effect: opening the FilamentHub tab **auto-writes overrides** (`render().then(() => pull(false))`, app.js line 161) — a mutation on tab-open that no UI convention prepares the user for.

## 2. The correct end-to-end model for filament display (spec)

**Principle: two layers, never merged destructively.**

- **Observed** (from hardware): gate occupancy, runout sensors, RFID reads, feeding head.
- **Desired/Asserted** (from humans + trackers): FilamentHub winners, manual overrides.

The current system collapses these into one `material` field and resolves conflicts by *deleting the assertion* (eject-debounce) or *hiding it*. Instead, every slot has a derived **reconciliation state**, computed server-side and rendered identically in every tab:

| State | Condition | Render |
|---|---|---|
| `VERIFIED` | occupied ∧ label ∧ (RFID agrees ∨ no RFID) | Solid card, color band, name + material, ✓ source badge ("RFID + Hub") |
| `ASSERTED` | occupied ∧ label ∧ no sensor confirmation | Solid card, name, "unverified" dot |
| `UNKNOWN_LOADED` | occupied ∧ no label | **Amber** card: "Filament present — unknown. *Identify →*" (opens picker) |
| `EXPECTED_NOT_LOADED` | empty ∧ label | **Ghost** card: dashed border, desaturated swatch, "Expected: SnapSpeed Red — *not loaded*", action "Load / Clear expectation" |
| `CONFLICT` | occupied ∧ label ∧ RFID disagrees | **Red** badge: "Tag says PETG Black, Hub says PLA Red — *pick one*" |
| `EMPTY` | empty ∧ no label | Muted "Empty" |

**Concrete behavior changes:**

1. **Kill the eject-debounce override delete for tracker-sourced labels.** An empty slot with a label becomes `EXPECTED_NOT_LOADED`, not a deletion. If auto-clear is wanted for *manually*-entered labels after a physical eject, emit an Activity event ("Cleared A2 label — spool ejected") so it is at least visible. Silent persistence-layer deletion of user/tracker data is never acceptable.
2. **Pull becomes a preview-then-commit reconcile.** `POST /pull` gains `dry_run`; the UI shows a diff table — *FilamentHub says / Printer senses / Proposed action* — before writing. Rows where desired ≠ observed occupancy are flagged: "Red → A2, but A2 is empty (will show as Expected)"; "A0 occupied but FilamentHub has nothing there — identify or ignore." One "Apply" button commits. The current fire-and-report-counts flow ("applied 2") is replaced by outcome language: "2 labels set (1 awaiting physical load), 2 occupied slots still unidentified."
3. **Pull must consume `aces_covered`** for prune scoping (fixes the vacated-ACE gap properly) and must warn — not fail — when it arrives empty on a schema-2 payload: "FilamentHub reported no coverage; clears skipped."
4. **Disputes become actionable:** spool *names* + swatches, deep-link per row into FilamentHub's resolution page, and a "keep current" affordance — not a text list of integer IDs.
5. **One label formatter, shared:** name ("SnapSpeed Red") primary, material · vendor secondary — in the dashboard slot cards, the FilamentHub grid, the toolhead cards, and the Fix-loadout wizard. The plugin grid's `material-or-"loaded"` rendering is deleted.
6. **One indexing scheme everywhere:** `A0…A3 / B0…B3` (letter-ACE + 0-based slot, matching the dashboard's swap labels like "A1 → B2"). The FilamentHub tab's `+1` is removed.

Should Pull *refuse* on mismatch? No — refusal punishes the common "labels first, filament in a minute" workflow. It should **warn and represent**: apply the label as `EXPECTED_NOT_LOADED` and make the mismatch a visible, persistent, resolvable state instead of either blocking or lying.

## 3. The golden path — and where it breaks

**Best-in-class:** *Insert a spool anywhere → within 5 seconds every screen shows the right name and color in the right slot → press Print → toolchanges cross ACEs invisibly → filament stays dry unattended → any fault names itself and offers a one-tap fix.*

Where the current product breaks it, in order: identity fragments at insert (RFID-less spool → "loaded"/blank, no identification prompt — break #1); tracker sync silently self-destructs on empty slots (Exhibit A — break #2); inactive ACEs show "?" so pre-print confidence requires switching ACEs manually (break #3); mid-print, a null head_source prints the *wrong color* with no pre-flight check that head_source ∧ sensors ∧ gcode requirements agree (break #4 — the Print-queue Fix-loadout wizard is the right idea, but it's optional and sidecar-dependent rather than a mandatory pre-print gate); drying never arms without DIY hardware and faults on defaults (break #5); recovery exits the product into G-code (break #6).

## 4. Quick wins (ship this week) vs. deeper redesigns

**Quick wins:**

1. Stop the eject-debounce from deleting overrides; render `EXPECTED_NOT_LOADED` ghost cards (backend: ~15 lines in `main.py` slot builder; frontend: one CSS class + label). This alone fixes Exhibit A's worst lie.
2. Make Pull's status honest: after write, re-read state and report "N labels on empty slots (shown as Expected)" and "M occupied slots unidentified" instead of raw applied/stale counts.
3. Fix the ±1 indexing in `filamenthub/static/app.js` (line 37, 68, 130) to match the dashboard's 0-based A/B scheme.
4. Show spool name (subtype) in the plugin grid; replace the "loaded" placeholder with "Filament present — unknown · tap to identify."
5. Replace dispute rows' spool IDs with names + a FilamentHub deep link.
6. Autodry: raise default `target_pct` to a reachable value (≥25), and surface `FAULTED` with plain-language text + Reset button in the plugin tab (not just `/reset-fault`).
7. Remove (or hide behind a flag) the legacy single-FSM autodry panel in the Dryer tab when the per-ACE plugin is deployed — one auto-dry UI.
8. Add "last seen HH:MM" to stale ACE blocks and a tooltip explaining *why* inactive ACEs are stale.
9. Announce auto-pull-on-open in the status line *before* it writes ("Syncing labels from FilamentHub…") and add a per-session opt-out.

**Deeper redesigns:**

1. The two-layer desired/observed slot model of §2, implemented in the state builder and consumed by *all* frontends (dashboard, plugin, hardware twin, Fix-loadout).
2. A mandatory pre-print filament gate: gcode requirements × head_source × sensors × labels, with the Fix-loadout wizard as its resolution UI — blocking wrong-color prints instead of documenting them in memory files.
3. Guided in-UI recovery flows replacing console recipes (`Mark loaded…`, `Clear head bookkeeping`, entangle-skip toggle) with persistence across restarts.
4. Fleet visibility: periodic short-lived polling (or cached snapshots with age) for inactive ACEs so "?" disappears from the product.
5. First-run setup wizard: detect ACE count vs. `ace_device_count`, detect pre-loaded heads, calibrate park-retract length interactively, verify humidity-sensor→ACE mapping with a "breathe on sensor 0" identify step.
6. Drift accounting: count coupling events per slot since last load; surface a proactive "check seating" chip before it becomes a mid-print failure.
